# 프론트 OCR 연결 검토·집 적용 — 2026-10-22

## 검토 대상과 범위

팀 main ec2811f, 프론트 브랜치 feat/frontend-prototype-ocr의 e73ccf6을 비교했다. 프론트 담당의 config.py / main.py / local_ocr.py와 테스트를 검토해 backend만 통합·보완했다. 프론트·machine·최상위 파일과 샘플 clean_rent_data.csv는 수정·반영하지 않았다. 특히 브랜치의 3행짜리 샘플 CSV로 실제 집 데이터를 교체하지 않았다.

## 수정한 문제

- 팀 main의 read_image는 site 인자가 없다. 기존 형태는 다방만 호출하고, site 지원 함수에만 site를 전달한다. 지원하지 않는 사이트는 422로 알려준다. 현재 팀 main 기준 지원은 다방 목록 캡처이며 직방 연결은 분석 담당의 별도 변경 확인이 필요하다.
- 집 Python 3.13 환경에 OCR이 없어, 기존 환경을 바꾸지 않고 별도 Python 3.12 OCR 가상환경을 준비했다. 실제 EasyOCR 1.7.2 / PaddleOCR 3.7.0 / PaddlePaddle 3.3.1을 설치했다.
- 두 엔진의 native DLL을 한 프로세스에서 불러오면 집 환경에서 충돌했다. 각 엔진을 별도 프로세스로 실행하고, 분석가의 기존 consensus 규칙으로 결과만 합친다. Windows 보안 설정을 해제하지 않았다.
- 기능 설정만 켜졌다고 준비됐다고 표시하지 않는다. 지정 실행 파일·분석 코드·엔진별 import를 확인하고 capabilities에 local_ocr_runtime / local_ocr_sites를 제공한다. 환경 미준비는 503, 동시 작업은 429, 각 엔진 120초 초과는 504. OpenAI로 임의 유료 전환하지 않는다.
- API 프로세스에서 엔진을 import하지 않아 월세 엔진에 영향을 주지 않는다. 요청 취소 후에도 실제 worker 작업이 끝날 때까지 다음 OCR을 막아 중복 CPU 작업을 제한한다. 임시 이미지·worker 결과 파일은 작업 종료/실패 시 정리한다.
- 합의된 카드라도 일부 필드가 없으면 해당 필드는 null인 확인용 초안을 만들 수 있다. 0원과 null을 구분한다. 주소·면적 기준·포함 항목을 추측하지 않고 항상 user_confirmed=false다.
- 여러 카드 선택은 소유자를 확인하고 새 추출 객체로 보존한다. 선택 원본 ID·카드 인덱스를 기록한다. 선택 요청의 Idempotency-Key 재시도와 충돌 처리를 지원한다.

## 기존 프론트와 호환되는 순서

공유 서버 모든 요청에 X-Team-Key, 세션 이후 Bearer 토큰을 사용한다. 접속키는 별도 전달하고 소스·로그에 넣지 않는다.

1. POST /sessions → GET /capabilities: image_provider / vision_configured / local_ocr_sites 확인.
2. POST /extractions: multipart file, 선택적 site=dabang. 기존 OpenAI 경로의 file-only 요청도 유지.
3. GET /extractions/{id}/listing-draft: 다중 후보면 ocr_cards를 표시.
4. POST /extractions/{id}/cards/{index}: 필요한 경우 카드 선택. 반환 draft.source_extraction_id를 사용.
5. 읽은 값 확인·누락값 수기 보완 → IMAGE_REVIEWED로 POST /listings. 사용자 확인 전 가격 비교 결과를 만들지 않는다.
6. 기존 POST /listings/{id}/analyses → GET /listings/{id}/report.

## 실제 확인과 남은 제한

- 실제 두 엔진으로 합성 다방 카드 이미지(보증금 1000만원 / 월세 60만원 / 면적 27㎡ / 관리비 7만원)를 읽었다. 두 엔진이 1개 카드에 합의해 EXTRACTED_NEEDS_REVIEW와 해당 값을 반환했다. 모델 다운로드 후 결합 실행은 약 7.8초였다. 실제 사용자 캡처 정확도 검증이나 전체 처리 시간 보장은 아니다.
- 프론트 브랜치의 클라이언트·입력 모델·관리비·주소 테스트 28개 통과. 별도 검토 복사본에서 실행했으며 프론트 원본은 변경하지 않았다. 이 결과는 실제 운영 화면 통합 시험과 다르다.
- **일부 정보만 있는 이미지의 앞단 검출 문제는 아직 남는다.** 분석가 ad_cards.py는 현재 층·면적·숫자 관리비가 있어야 카드 튜플을 만든다. backend는 반환된 부분 초안을 받을 수 있지만, 파서가 카드 자체를 반환하지 않으면 복원할 수 없다. 누락값을 임의로 보충하지 않았다. 분석 담당이 부분 카드 반환 계약·카드 경계와 필드별 합의 기준을 보완해야 한다.
- 카드/신분증 등 일반 문서 OCR 서비스가 아니다. 지원된 부동산 목록 캡처 범위만 확인했으며 다른 이미지·상세화면·실제 3건 고지서 정확도는 검증하지 않았다.
- 프론트 브랜치에 관리비의 실제 사용량에 따라 달라질 수 있다는 안내 문구는 존재한다. 캡처 입력 위 서비스 설명·최종 CSS·게시 링크 반영은 프론트 담당 확인이 필요하다.
- 관리비 계산 활성화 정책은 이번 OCR 작업과 별개로 유지한다. 실제 3건 비교·방식 선택 완료로 보고하지 않는다.

프론트 전달 초안: “OCR backend 변경을 검토하고 집 실행 환경·카드 선택·누락값 초안 처리를 보완했습니다. 현재 분석 main은 다방 목록을 지원합니다. 실제 두 엔진의 합성 이미지 검증과 API 경계 시험 결과를 확인했습니다. 새 서버 주소와 별도 접속키로 실제 캡처→선택→보완→저장→월세 결과를 확인해 주세요. 이미지에 면적/관리비 등이 없어 0개가 나오는 문제는 분석 파서 보완이 필요하며, backend가 값을 추측해 채우지는 않습니다.”
