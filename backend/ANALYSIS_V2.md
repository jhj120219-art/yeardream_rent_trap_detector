## 현재 진행 범위 — 2026-10-20 확정

**동네 비교로 진행한다.** 같은 건물 우선 비교와 관리비는 보류한다.
`SAME_BUILDING_ENABLED=false`가 기본값이며, 건물 자료가 들어와도 자동으로 같은 건물 비교를 켜지 않는다. 분석 원본은 보존하고 백엔드가 사용하는 정책 복사본에서 해당 단계를 끈다.
같은 법정동의 유사 거래부터 찾고, 부족하면 기존 규칙에 따라 조건을 완화하거나 같은 구로 넓힌다. 화면에는 실제 비교 범위를 표시한다. 현재 범위를 진행하기 위해 건물 동수 CSV를 요청할 필요는 없다. 아래 같은 건물 설명은 향후 범위를 바꿀 때 참고할 보존 기록이다.

### 화면과 서버가 주고받는 순서

사용자는 화면에서 입력하고 확인 버튼만 누른다. 아래 연결은 프론트 담당자가 구현한다.

| 순서 | 쉬운 설명 | 프론트 담당자용 연결 |
| --- | --- | --- |
| 1 | 팀원만 서버에 들어오도록 접속키를 사용 | 별도 전달한 키를 기존 인증 규격으로 사용 |
| 2 | 내 매물을 구분할 임시 이용표 발급 | POST /sessions |
| 3 | 비교 가능한 지역·건물 종류 표시 | GET /capabilities 및 GET /locations |
| 4 | 사용자가 확인한 매물 정보를 저장 | POST /listings |
| 5 | 저장한 매물을 동네 실거래와 비교 | POST /listings/{id}/analyses |
| 6 | 가격 범위·차액·표본 수·보류 이유 표시 | GET /listings/{id}/report |

백엔드는 저장·분석 호출·결과 전달을 맡고, 프론트는 입력칸·버튼·결과 화면을 연결한다. 접속키는 문서나 채팅에 적지 않고 따로 전달한다. 프론트 실제 화면에서의 최종 확인은 별도 작업이다.

# 분석가 개선판 실제 연결

## 이번에 연결한 것

분석가가 제공한 `machine/analysis_internal/engine_v2.py`, `configs/candidate_v2.json`, `trust_coef_v2.json`을 원본 그대로 실행한다. 백엔드 `app/analysis_v2.py`가 기존 입력을 분석가 입력으로 바꾸고, 결과를 기존 v1.1 필드에 맞춰 저장·반환한다. 별도 가격 계산기를 만들거나 분석 원본을 수정하지 않았다.

입력 → 사용자 확인 → MySQL 저장 → **개선판 실행** → 결과 저장 → 기존 보고서 조회로 연결했다. 관리비·캡처 실험과 별개이며 관리비는 계속 보류다.

## 실제 실행 설정과 API

```dotenv
ANALYSIS_ENGINE=v2
V2_ENABLED=true
SAME_BUILDING_ENABLED=false
# 분석가가 제공한 성공 조회 캐시가 있을 때만 지정한다. 없으면 비워둔다.
BUILDING_CACHE_CSV=
```

기본 설치 설정은 v1을 유지한다. 해당 로컬 환경 파일에서 위 설정을 선택하면 기존 `POST /listings/{id}/analyses`가 개선판을 실행한다. `?engine=v1` 또는 `?engine=v2`로 명시할 수도 있다. 개선판을 준비하지 않은 서버에서 v2 요청은 503이며, 조용히 v1으로 바꿔 실행하지 않는다. `/ready`도 기본 엔진이 v2인데 준비되지 않으면 503이다.

기존 매물·분석은 그대로 남는다. 새로운 분석은 새 Idempotency-Key를 사용한다. 같은 키를 다른 엔진에 재사용하면 409다. v1의 기존 재시도 fingerprint는 유지했다. 기존 입력·응답 상태와 금액 만원·면적 ㎡ 단위도 유지한다.

`GET /capabilities`: `analysis_engine`, `v2_status`, `same_building_first_supported`, `building_cache_status`를 확인한다. 현재 `same_building_first_supported=false`, `same_building_first=false`로 고정한다. 실제 결과의 `reference.conditions.scope`를 표시한다.

## 지번 입력

기존 `listing` 안에 `main_no`(본번), `sub_no`(부번)를 선택적으로 넣는다. 각각 1~4자리 숫자 문자열 또는 null이다. 본번은 1 이상, 부번만 입력은 불가다. 본번만 있으면 부번은 0000으로 맞춰 분석한다. 건물의 동·호수나 층수와 혼동하지 않는다. 임의 주소 문자열에서 지번을 추측하지 않는다.

예: 기존 확인된 입력에 `main_no: "279"`, `sub_no: "235"`를 추가한다. 법정동명만 쓰면서 동일 이름의 코드가 여러 개이면 지번 코드를 추정하지 않고 같은 건물 비교를 적용하지 않는다. 가능한 경우 `/locations`나 주소 후보에서 선택한 법정동 코드를 사용한다. 주소 검색 외부 키 검증은 별도 남아 있다.

## 같은 건물 비교는 확인 자료가 있을 때만

필요한 CSV 열: `CGG_CD,STDG_CD,MNO,SNO,ok,n_main`. 구·법정동은 각각 5자리, 지번은 1~4자리 숫자다. `ok=True`로 성공 조회한 행만 사용한다. 실패·미조회 지번을 1동으로 만들지 않는다. 같은 지번의 충돌하는 건물 수·잘못된 코드는 전체 연결을 거부한다. 원본 캐시는 저장소 밖에 보관하며 Git에 올리지 않는다.

분석가 고정 정책에 따라 같은 지번의 주건축물이 정확히 1동이고, 같은 유형·조건·기준일 이전 거래가 충분해야 stage 0을 적용한다. 건물 캐시가 없으면 `building_cache_status=MISSING`이고 동네→조건 완화→구 비교로 넘어간다. 결과의 `analysis_engine.stage0_reason`에 미확인 이유를 기록한다. 조회 키와 캐시 모두 현재 PC에서 발견하지 못했다. **현재 실데이터에서 같은 건물 비교가 확인됐다고 보고하지 않는다.** 건축물대장은 현재 상태일 수 있어 과거 계약 당시와 차이 날 수도 있다.

## 분석 담당 협의안: 혼합 용도 지번 보호

발견 근거: 원본 `_stage0()`의 묶음 키는 구·동·본번·부번이고 유형 필터가 없다. 같은 지번에 아파트와 오피스텔이 있으면 두 유형의 월세가 섞일 수 있다. 백엔드는 주택 유형별로 입력 데이터를 나누어 원본 엔진에 전달한다. 원본 파일·계수·정책 수치는 변경하지 않는다.

입출력 검사 예: 같은 지번에 합성 아파트 12건(약 50만원) + 오피스텔 12건(250만원)을 넣으면, 아파트 입력의 같은 건물 표본은 12건이고 중앙값은 약 50만원이어야 한다. 24건·약 150만원으로 섞이지 않는 것을 검사했다. 분석 담당은 이 필터를 정식 엔진에도 반영할지 확인해야 한다. 해당 보호를 적용한 백엔드의 정확도를 과거 평가 수치(89%·90.2% 등)로 주장하지 않는다.

## 결과와 판단 보류

- 기존 `status`, `price_label`, `stage`, `sample_count`, `prices_10k_krw`, 중앙값 대비 차액·차이율을 제공한다. 분석가 엔진이 산출한 분위값과 라벨·신뢰도 등급을 사용한다.
- 같은 건물 비교면 `stage=0`, `reference.conditions.scope_code=SAME_LOT_VERIFIED_SINGLE_MAIN`. 동/구 비교면 LEGAL_DONG/DISTRICT다. 기존 scope는 한국어 설명을 유지한다. 같은 건물 기간은 정책의 730일을 반환하고 월수로 임의 변환하지 않는다. 시점·선별 조건은 실제 적용된 정책을 기록한다.
- 경계 5% 마진, 낮은 신뢰도, 구 전체 비교, 단독다가구 층 미확인·지하, 입력 자릿수 의심은 분석가 시연의 보류 규칙에 맞춰 기존 상태로 전달한다. 공급·계약면적 보류, HIGH에서만 최상위 라벨, 단독다가구 HIGH·Q75×1.10 조건은 기존 v1.1 보호를 유지한다. 내부 시연의 완화된 부분을 그대로 고객 API에 적용하지 않은 차이이므로 분석 담당의 정식 계약 확인이 필요하다.
- `analysis_engine`에 후보 정책 버전·백엔드 어댑터 버전·비교 출처·같은 건물 보류 이유를 남겨 재조회할 수 있다. 이전 v1 결과를 v2 결과로 바꾸지 않는다.
- 엔진이 반환하지 않는 percentile·개별 거래 목록은 만들지 않는다. report의 거래 목록은 계속 null/NOT_PROVIDED_BY_ANALYSIS다. 별도 거래 ID·선별 행 반환은 분석 담당의 추가 규격이 필요하다.
- 신뢰도는 등급·설명으로 전달한다. 사기 확률·현재 매물의 정확도·임의 유사도 %를 생성하지 않는다.

## 검증·아직 남은 것

합성 표본에서 확인 건물 stage0, 미조회·실패 캐시의 fallback, 유형 혼합 차단, 경계 보류, 미확인 입력·공급면적·자릿수 의심, 기존 v1 선택·재시도, MySQL 저장·독립 HTTP 프로세스 재시작 후 보고서 동일 조회를 확인한다. 실제 CSV에서도 개선판의 동네 비교 실행을 확인했다. 합성 캐시의 '1동'을 실제 자료로 사용하지 않는다.

배포 Docker에는 원본 엔진·공통 모듈·정책/계수 JSON만 포함하도록 준비했다. 현재 PC에는 Docker가 없어 새 이미지 빌드 자체는 미검증이다. 원본 NumPy 날짜 연산에서 폐기 예정 경고가 관찰됐으며 원본을 임의 수정하거나 경고를 숨기지 않았다.

분석 담당 요청(건물 캐시는 현재 범위에서 요청하지 않음): 유형 혼합 필터·공급/계약면적 보호의 정식 규칙 확인, 개별 비교 거래 행 반환 규격. 프론트 요청: 기존 결과 화면에서 reference의 실제 범위·보류 이유와 v2 버전을 표시. 관리비는 보류. 요청은 초안이며 직접 보내지 않았다.
